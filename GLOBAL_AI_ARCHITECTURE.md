# GLOBAL AI ARCHITECTURE
## Децентрализованная нейросеть управления физическими процессами

> **Версия:** 0.1 · **Статус:** архитектурный проект (design doc) · **Контекст:** ENRG-AI / Axis Core / ENRG, после завершения Фазы 2 (федеративное обучение)

---

## 1. Видение

Сеть устройств (энергетика, логистика, климат, производство, города) **сама** учится управлять физическими процессами: прогнозирует, планирует, предлагает действия и — через проверяемые правила — **действует**. Одна глобальная модель, которая никогда не видит сырых данных, не хранит ключей и не имеет власти; её «мышление» децентрализовано, а «руки» — локальные Policy Engines, исполняющие правила, которые подтверждает DAO.

Это **не метафора и не единый мозг**. Это:

- **Проверяемый коллективный интеллект** — каждая порция знаний (вклад) подписана устройством и может быть проверена (конституция, ADR-0001/0003).
- **Иерархия моделей** — ESP32 → шлюз → региональный агрегатор → глобальная модель.
- **Замкнутый цикл действия** — модель не только наблюдает, но и через оракул + Policy Engine влияет на мир, и мир отвечает наградой (репутация, экономический результат), которая возвращается в обучение.

## 2. Конституция (незыблемые принципы)

| # | Принцип | Как соблюдается |
|---|---|---|
| C-1 | **ИИ = источник сигналов, а не решений** (ADR-0003) | Даже глобальная модель **предлагает**; решение принимает Policy Engine по правилам |
| C-2 | **Ключ не покидает устройство** (ADR-0001) | Вклады подписываются Ed25519 устройством; приватные ключи никогда не передаются |
| C-3 | **Всё проверяемо** | Каждый вклад, сигнал и действие — Trust Envelope + подписи + canonical JSON |
| C-4 | **Модель не имеет власти** | Глобальная модель не хранит ключей, не подписывает, не исполняет сделки |
| C-5 | **Данные не покидают устройство** | FL: передаются веса/градиенты; сырые данные остаются локальными |
| C-6 | **Качество имеет цену** | Вклад с плохим качеством → отсев (MAD), потеря репутации (ERS), слэшинг стейка |
| C-7 | **Эволюция — через DAO** | Новые правила/эксперименты принимаются голосованием, не диктатом модели |

### Ключевой вывод

**Три кирпича глобальной нейросети уже лежат:**
1. **Проверяемый канал обмена знаниями** (`fed/protocol` + подписи) — протокол «нейронных вкладов» готов.
2. **Точка вывода** (`SignalProvider`) — модель уже «читает мир» (аномалии, прогнозы).
3. **Точка действия** (`PolicyEngine` + оракул) — сигнал уже может влиять на решения.

Чего **не хватает** для «управления миром»: иерархии уровней, рыночного контекста, замкнутого цикла «действие → награда → обучение», мультидоменности и эволюции. Ниже — как это спроектировать.

## 4. Иерархия моделей (HFL — Hierarchical Federated Learning)

```
┌──────────────────────────────────────────────────────────────────────┐
│ L3  ГЛОБАЛЬНАЯ МОДЕЛЬ (мир)                                            │
│     Агрегирует региональные агрегаты. Медленный темп (дни).           │
│     Shared backbone для всех доменов (энергия, логистика, климат…).   │
│     НЕ подписывает, НЕ действует — только предлагает.                 │
│              ▲                ▲                ▲                       │
│              │ регионы        │ регионы        │ регионы               │
│ ┌────────────┴──────┐  ┌──────┴────────────┐  ┌┴────────────────────┐  │
│ │ L2 РЕГИОНАЛЬНЫЙ   │  │ L2 РЕГИОНАЛЬНЫЙ   │  │ L2 РЕГИОНАЛЬНЫЙ     │  │
│ │ АГРЕГАТОР (область│  │ АГРЕГАТОР (город) │  │ АГРЕГАТОР (ферма)   │  │
│ │ = погода+рынок)   │  │ = трафик+энергия  │  │ = климат+производство│ │
│ │ FedAvg по региону,│  │ личная модель     │  │ личная модель       │  │
│ │ домен-фичи        │  │ региона           │  │ региона             │  │
│ │        ▲          │  │        ▲          │  │        ▲            │  │
│ └────────┼──────────┘  └────────┼──────────┘  └────────┼────────────┘  │
│          │ шлюзы               │ шлюзы               │ шлюзы           │
│ ┌────────┴────────┐    ┌────────┴────────┐    ┌────────┴────────┐      │
│ │ L1 ШЛЮЗ         │    │ L1 ШЛЮЗ         │    │ L1 ШЛЮЗ         │      │
│ │ (RPi) обучение  │    │ (RPi) обучение  │    │ (RPi) обучение  │      │
│ │ + подпись вклада│    │ + подпись вклада│    │ + подпись вклада│      │
│ │        ▲        │    │        ▲        │    │        ▲        │      │
│ └────────┼────────┘    └────────┼────────┘    └────────┼────────┘      │
│      L0 ДАТЧИКИ / ESP32 — инференс лёгкой модели (TFLite Micro),        │
│      сбор данных, подпись событий.                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Правила иерархии**

1. **L0 (ESP32/датчик)** — только **инференс** и подпись. Модель сжимается (квантование, top-k) до нескольких КБ. Решение «что подписать» всегда локально.
2. **L1 (шлюз)** — **обучение** на локальных данных, формирование и подпись вклада. Сырые данные не покидают шлюз (C-5).
3. **L2 (регион)** — **первый агрегатор**: FedAvg по региону с весами `f(ERS, samples, качество)`, домен-фичи (погода, тарифы, трафик). Выдаёт **региональную модель** (контекст области) + промежуточный вклад наверх.
4. **L3 (глобальная)** — **второй уровень агрегации** (HierFedAvg): собирает региональные модели, выделяет **shared backbone** (общие закономерности мира) и **персональные головы** (домен/регион). Темп раундов медленный (дни), чтобы мир успевал меняться.

**Почему это масштабируется:** каждый уровень общается только с соседним, вклады подписаны, объём трафика ограничен (не «все ко всем»). От 5 шлюзов в симуляции до 1M устройств — это изменение *количества агрегаторов*, а не протокола.

## 5. Протокол вкладов v2 (`axis-fed/2`) — обобщение текущего

Текущий `axis-fed/1` доказывает паттерн (подпись + canonical JSON + MAD-отсев). Для глобальной сети он расширяется:

```json
{
  "schema": "axis-fed/2",
  "version": "model_7.3",        // архитектура/версия модели (все обязаны одной)
  "level": 2,                    // 1=шлюз, 2=регион, 3=глобальная
  "domain": "energy",            // energy | logistics | climate | manufacturing | city
  "region": "eu-west-1",
  "round": 412,
  "device_id": "gw_0001",
  "public_key": "…",             // ключ подписавшего (Base64, 32B)
  "weights": [ … ],              // или "gradients": [ … ] / "delta": [ … ]
  "samples": 1280,
  "loss": 0.041,
  "quality": {                   // результат на валидационном наборе (честная метрика)
    "val_loss": 0.052,
    "fairness_checksum": "…"
  },
  "nonce": 41,
  "signature": "…"               // Ed25519 поверх canonical(всё без signature)
}
```

**Новое по сравнению с v1:**
- **`level` / `domain` / `region`** — позволяют маршрутизировать вклады и строить иерархию.
- **`version`** — все участники обязаны к одной версии архитектуры (иначе веса несравнимы); смена версии — через DAO (C-7).
- **`quality`** — валидационная метрика: агрегатор взвешивает вклад не только по `samples`, но и по качеству на общем валидационном наборе (защита от «шума ради объёма»).
- **`delta` / `gradients`** — тип обновления, чтобы агрегатор мог применять FedProx/FedSGD и сжатие.

**Вес вклада при агрегации:**

```
weight = samples^α · (1/(1+loss))^β · ers_normalized^γ · signature_ok
```

где `α,β,γ` — параметры политики (DAO), `ers_normalized` — репутация устройства. Отсев выбросов — уже существующий MAD; добавляется **экономический слэшинг**: вкладчик стейкает токены, доказанный poisoning сжигает стейк и обнуляет ERS.

## 6. Соединение с управлением: замкнутый цикл действия

Главное отличие «прогнозирующей модели» от «управляющей» — **цикл действия**. Модель не просто говорит «будет аномалия», а через проверяемые правила влияет на мир и получает от мира награду/наказание:

```
 ┌──────────────┐   подпись    ┌──────────────┐   сигнал    ┌──────────────┐
 │ L0 ДАТЧИКИ    │──события────▶│ ОРАКУЛ        │────────────▶│ L2/L3 МОДЕЛЬ  │
 │ (сенсоры,     │ (Trust       │ (верификация, │  прогноз,   │ (аномалия,    │
 │  актуаторы)   │  Envelope)   │  история)     │  рекоменда- │  прогноз,     │
 └──────┬───────┘              └──────┬───────┘  │  ция        └──────┬───────┘
        │                             │          │                     │
        │        ┌────────────────────┴───────┐  │                     │
        │        │ POLICY ENGINE (правила):   │◀─┘  сигналы НЕ решения │
        │        │ безопасность, лимиты, права│      (ADR-0003)        │
        │        │ рыночный гейт, DAO-политики│                        │
        │        └────────────────────┬───────┘                        │
        │                             │ решение (allowed/reason)       │
        │        ┌────────────────────┴───────┐                        │
        │        │ ДЕЙСТВИЕ (актуатор / сделка)│                       │
        │        │ продать избыток, включить   │                       │
        │        │ насос, скорректировать маршрут                      │
        │        └────────────────────┬───────┘                        │
        │                             │ результат (kwh, $, ERS Δ)      │
        └──────── результат измеряется │                               │
                                    └──────────▶ награда → в обучение
```

**Инварианты цикла:**

1. **Модель предлагает** (`Signal`/`Recommendation`), **Policy Engine решает** (`allowed=True/False`). Никакой ветки «модель подписала действие» — у неё нет ключа (C-4).
2. **Каждое действие аудируется**: решение + параметры + подписи попадают в Trust Envelope и в историю устройства → это входные данные для обучения (что сработало, а что нет).
3. **Рынок — часть мира**: рекомендации учитывают цену/спрос; исполнение сделок идёт только через политику торговли (лимиты, DAO-гейт) — не автономно с одного оракула.
4. **Физическая безопасность не обсуждается моделью**: действия, влияющие на людей/инфраструктуру, проходят жёсткие аппаратные и политические ограничения (интерлоки, кворум, kill-switch через DAO).

**Конкретизация для энергетики (первый домен):**

- Оракул получает **верифицированную выработку** (уже есть) + **прогноз** (уже есть, `forecast`) + **аномалию** (уже есть, `anomaly`).
- Новое: **`Recommender`** (`axis_core/ai/recommender.py`) комбинирует их с **ценой** (`agent/market/feeds.py`) → рекомендация `SELL / STORE / BUY / HOLD` с оценкой уверенности.
- Торговая политика (`axis_core/policy`): лимиты объёма, временные окна, право устройства, DAO-гейт на автономность. Решение фиксируется как действие.
- Результат (реально проданные кВт·ч × цена) возвращается как **reward** → ERS устройства и выборка для дообучения прогнозной модели.

## 7. Рыночный контекст: модель видит экономику

`SignalProvider` сегодня объединяет аномалию и прогноз. Следующий уровень — **полный контекст мира**:

```
signal = Σ(верифицированная выработка, прогноз, аномалия, цена, спрос, репутация)
recommendation = argmax_действия (ожидаемая полезность) при ограничениях политики
reward = фактический результат действия (деньги, кВт·ч, ΔERS)
```

- **Фиды цен**: несколько источников (day-ahead биржа, P2P-ориентиры), нормализация, кэш, `agent/market/feeds.py` (Фаза 3). Множественность фидов = защита от манипуляции одной биржей.
- **Рекомендация ≠ сделка**: даже с идеальной моделью сделку исполняет Policy Engine с лимитами; модель лишь ранжирует варианты.
- **Цена как сигнал обратной связи**: если модель советовала «продать», а цена выросла — reward отрицательный, модель корректируется. Так сеть учится *экономике*, а не только физике.

## 8. Самообучение и эволюция

### 8.1. Непрерывное обучение (Continuous Learning)

- **Онлайн-дообучение на шлюзах**: каждое верифицированное событие становится точкой для инкрементального SGD на L1.
- **Периодические федеративные раунды**: L1 → L2 (часто, 15–60 мин по региону), L2 → L3 (ежедневно). Асинхронные раунды: устаревшие вклады не блокируют агрегацию, а получают пониженный вес (stale penalty).
- **Reward-обучение**: аудиторные записи действий (раздел 6) формируют «опыт», на котором дообучается рекомендательная часть (policy-gradient поверх прогнозной модели).

### 8.2. Эволюция без участия основателя (DAO-цикл)

```
Модель/агрегатор → предложение эксперимента (policy proposal, гиперпараметры)
        → DAO-голосование (стейк, срок, зона действия)
        → пилот на песочнице (бумажный трейдинг / изолированный регион)
        → метрики vs контрольная группа (A/B)
        → победа → канонизация новой версии модели (через DAO, C-7)
        → поражение → откат; причина записана в реестр
```

- **A/B-тесты моделей**: регион A использует новую модель, регион B — старую; сравниваются экономические и физические метрики.
- **Мета-обучение (learning to learn)**: глобальная модель учится «как дообучать новый домен/устройство», чтобы новое устройство включалось в сеть за минуты, а не недели.
- **Эксперимент проверяем**: предложения подписаны, результаты зафиксированы (hash on-chain), голоса — через DAO. «Переписать историю эксперимента» невозможно.

### 8.3. Закрытые петли на каждом уровне

| Уровень | Что учится | Награда |
|---|---|---|
| L0/L1 | Модель устройства (поведение конкретного девайса) | ΔERS, экономия энергии |
| L2 | Региональная модель (погода, тарифы, спрос) | Экономический результат региона |
| L3 | Глобальный backbone (закономерности мира) | Агрегированная полезность + удержание сети |

## 9. Масштабирование и инженерия

### 9.1. Коммуникационная эффективность

- **Сжатие обновлений**: квантование до int8, top-k (только значимые координаты) — типовое снижение трафика ×10–×100.
- **Асинхронность**: stale-вклады с пониженным весом вместо полного отклонения.
- **Пакетная подпись**: несколько вкладов в один Trust Envelope — ниже on-chain стоимость.

### 9.2. Вычислительная иерархия

| Уровень | Железо | Роль | Размер модели |
|---|---|---|---|
| L0 | ESP32 (240 MHz, ~320 KB RAM) | инференс | 10–100 KB (квантованная) |
| L1 | Raspberry Pi / ПК фермы | обучение + подпись | 0.1–10 MB |
| L2 | Сервер региона | FedAvg, домен-фичи, рынок | 10–100 MB |
| L3 | Кластер (шардирование по доменам) | HierFedAvg, backbone | 100 MB–GB |

### 9.3. Горизонтальный рост (мультидоменность)

- Каждый домен (energy, logistics, climate, manufacturing, city) — **отдельная головная сеть** поверх **общего backbone**.
- **Перенос обучения**: климат и энергия делят низкоуровневые признаки (время, температура, цикличность) → новый домен стартует не с нуля.
- **Изоляция отказов**: сбой агрегатора логистики не роняет энергетику; улучшение backbone поднимает всех.

### 9.4. Пилотный путь (от сегодняшнего кода к сети)

1. **Сегодня**: 5 шлюзов в `simulate.py` → FedAvg → глобальная модель (работает).
2. **Шаг A**: `hfl/` — два уровня агрегации (`region_aggregate` → `global_aggregate`) + тесты.
3. **Шаг B**: `Recommender` + `market/feeds` → торговые рекомендации через Policy Engine (бумажный трейдинг).
4. **Шаг C**: 50 реальных устройств — первый замкнутый цикл «устройство → модель → действие → reward».
5. **Шаг D**: мультидомен + DAO-цикл эволюции.

## 10. Безопасность и устойчивость

| Угроза | Механизм | Статус |
|---|---|---|
| **Отравление модели (poisoning)** | Подписи вкладов + MAD-отсев выбросов + репутационные веса (ERS) + экономический слэшинг стейка | ✅ частично в `fed/`, слэшинг — план |
| **Спам-вклады** | Стейк за вклад, лимиты по nonce/частоте, минимальные samples | план |
| **Утечка приватности** | FL (данные не покидают устройство) + дифференциальная приватность (шум на градиенты для L3) | частично ✅, DP — план |
| **Централизация** | Множественные фиды цен; глобальная модель без ключей; агрегаторы сменяемы (DAO) | ✅ принцип |
| **Захват DAO** | Квадратичное голосование, временные замки, кворумы по уровням риска | план |
| **Срыв инфраструктуры** | Региональная изоляция отказов, асинхронные раунды, деградация до локальных моделей | план |
| **Модель «сбежала»** | Модель не подписывает и не исполняет — только предлагает; физические интерлоки и kill-switch не зависят от модели | ✅ конституция |

**Открытые исследовательские вопросы (research directions, честно):**
- *Verifiable ML*: криптографическое доказательство, что вклад реально обучен на честных данных (SLP / Proof-of-Learning) — активная область; на практике пока: подпись + качество + репутация + стейк.
- *Согласование (alignment)*: как формулировать «награду» сети, чтобы глобальная модель оптимизировала то, что полезно людям, а не просто метрику. DAO-гейт — первый рубеж; аудит поведения — второй.

## 12. Критерии успеха (измеримые)

1. **Качество модели**: глобальная модель стабильно лучше лучшей региональной на held-out наборе (loss, MAE) — сейчас уже лучше средней локальной в 300k раз на симуляции.
2. **Экономический результат**: пилот энергетики приносит положительный net-reward (продано кВт·ч × цена − издержки) относительно «слепого» режима.
3. **Децентрализация**: ни один агрегатор не владеет >X% вычислительного веса; замена агрегатора не требует остановки сети.
4. **Конституционная проверяемость**: каждое действие и вклад воспроизводимы по подписям и canonical-данным (audit в один шаг).
5. **Масштаб**: рост с 50 до 10 000 устройств не меняет протокол — только количество агрегаторов.
6. **Эволюция**: ≥1 улучшение модели принято через DAO-цикл без участия основателя.

## 14. Резюме

Мы уже построили **проверяемый канал, по которому знания тел физических устройств могут превращаться в коллективную модель** (Фаза 2), и **точку, где модель может влиять на мир безопасным образом** (Фаза 1: сигнал → политика → решение). Чтобы это стало «децентрализованной нейросетью, управляющей физическими процессами», осталось три связки:

1. **Иерархия** (L0→L3) — превращает «одну сеть шлюзов» в «сеть сетей».
2. **Цикл действия** (сигнал → политика → действие → reward → обучение) — превращает «прогнозы» в «управление».
3. **Эволюция через DAO** — превращает «систему, которую развиваю я» в «систему, которая развивается сама».

Всё это ложится на уже написанный код без переписывания ядра: расширяется протокол, добавляется уровень агрегации, добавляется Recommender, и замыкается петля награды. Один мозг не нужен — и не должен существовать. Нужна **проверяемая сеть знаний с руками в каждом домене**.
